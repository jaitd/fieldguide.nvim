# The plugin index

One SQLite file describing the Neovim plugin ecosystem, so the agent can answer
questions about plugins that are **not** installed.

For installed plugins, fieldguide answers from the editor instead:
`nvim_docs` resolves helptags at the revision on disk, and `grep` reaches the
whole of `lazy_root` through the read-only doc zone. The index covers what the
live session cannot:

| | |
|---|---|
| **discovery** | plugins you do not have |
| **withdrawal** | archived, or superseded by a named successor |
| **integration** | what works with what |
| **freshness** | upstream moved past the pinned revision |

Withdrawal is based only on what the maintainer declared: the GitHub archive
flag, or the repository saying of itself that something replaced it. Time since
the last commit is stored and reported, but never marks a plugin as withdrawn.

## Getting one

Users run `:FieldguideIndex`. From a checkout:

```sh
mise run index:fetch     # download the published index
mise run index           # build one from scratch (slow, needs a token and a provider)
```

## Versioning

The index is **released on its own track**, independent of fieldguide's
version; any fieldguide version can use any index its reader accepts.

`meta.schema` is a semver describing the shape of the file:

| | |
|---|---|
| major | a reader at the old version cannot cope — a column dropped, renamed, retyped, or a value whose meaning changed |
| minor | additive: a new column or table an older reader can ignore |
| patch | how a column is populated, shape identical |

A reader accepts a range: major equal, minor and patch at least its own. So
adding a column does not lock out readers already installed. An index outside
the range is refused entirely.

`SCHEMA_VERSION` in `build.ts` and `READS_SCHEMA` in `extension/plugins.ts` are
the two halves. Change one and the tests will tell you about the other.

## Releases

One release per schema major, with the asset replaced in place:

```
index-v1/nvim-plugins.db.gz
index-v1/nvim-plugins.db.gz.sha256
```

The digest is served by the same host as the file, so it detects a truncated or
corrupted transfer and nothing else. It is **not** a signature and does not
protect against a compromised release. The fetcher downloads the digest first,
which also tells it cheaply whether anything has changed.

Tags carry the schema major, not a date, so a reader can always find the newest
index it can read. The precise schema version is in the file's `meta` and the
release title, and `built_at` records when the data was collected.

A new schema major gets a new tag, `index-v2`, and `index-v1` keeps being
published until it is retired, so existing installs keep working.

The weekly job replaces the asset **only when something material changed**:
the plugin set, a withdrawal flag, a blurb, a category, or keywords. Star
counts and `last_push` alone do not trigger a release. `changed.ts` makes the
decision and prints its reasoning, including the `last_push` count, to the job
log.

## What ships, and what does not

No third-party prose. READMEs and help files are read during the build and
discarded. The index contains metadata, the CC0 blurbs from awesome-neovim, and
blurbs generated by the builder. Third-party text is not redistributed, since
not every repository in the corpus has a licence that would allow it.

## How a plugin gets described

Plugins listed in awesome-neovim keep its curated blurb and category. The rest,
and curated entries whose GitHub description does not say what the plugin does,
are described by a model from the repository's **shape** as well as its prose,
in this order:

```
top-level files    colors/ means colorscheme and nothing else does
lua/ modules       gitsigns is blame.lua, hunks.lua, diffthis.lua
doc/               the author's own help file
README             last, and labelled as untrusted marketing copy
```

The model returns a blurb, a category from the fixed list in
`categories.json`, and three to eight **keywords**. Keywords map the terms
users search for to the terms authors use, such as "autocompletion" alongside
"completion" and `gutter` alongside `statuscolumn`. This happens once at build
time, with no query-time inference and no runtime dependency.

Each blurb is cached in `blurbs.json` against the release tag it describes, or
the commit when there is no tag. CI commits that file back, so a weekly rebuild
only asks the model about plugins that are new or have moved.

## Guards

The material fed to the model is untrusted text, and its output ends up in a
database read by an agent that can write to your config. Four checks apply:

- **Constrained output.** The category must be one of the 72 in
  `categories.json`; a blurb over 200 characters or an empty keyword list is
  refused rather than repaired. A rejected plugin falls back to its GitHub
  description.
- **The committed cache.** Every generated blurb appears as a reviewable diff
  in `blurbs.json` before it is published.
- **A structural cross-check.** A claimed category is tested against the file
  tree: a colorscheme must have `colors/` or `lua/`, and a repository with
  `colors/` but no `plugin/` or `doc/` must be a colorscheme.
- **Grounding in the file tree.** Descriptions are based on the code's layout,
  not only the README. This makes a misleading description harder to induce,
  but does not rule it out.

## The graph

`edge` records **how each edge was concluded**:

- `lazy-spec` — the plugin's own README declares it in a `dependencies` block.
- `naming` — the repo name says so, `cmp-*` extending `nvim-cmp`.

Every edge carries its evidence, and `nvim_plugin` reports it, so a caller can
tell a declared dependency from one inferred from a name.

## Ranking

`plugin_fts` is a contentless FTS5 index over name, blurb, keywords and
description, weighted in that order. Results combine text relevance with
popularity; the coefficient between them is fitted against the sample queries
in `tests/plugins.test.ts`. Search results exclude the `Pre-made Configuration`
and `Plugin Manager` categories.

## Running the builder

It needs a GitHub token — `GITHUB_TOKEN`, or whatever `gh auth token` prints —
and, unless given `--no-llm`, a provider for the blurbs:

```sh
FIELDGUIDE_INDEX_PROVIDER=openrouter \
FIELDGUIDE_INDEX_MODEL=deepseek/deepseek-v4.1-flash \
  node tools/plugin-index/build.ts out.db
```

Blurbs are written with thinking off (`FIELDGUIDE_INDEX_THINKING=off`, passed
to pi as `--thinking`). With thinking on, or set empty to use pi's default,
calls take minutes each and hit the per-plugin timeout.

Run `pi update --models` first, with the provider's key in the environment.
pi's bundled model catalog can lag OpenRouter's, and a model missing from it
runs as a custom id without reasoning support: pi warns `Using custom model id`,
ignores `--thinking off`, and the model reasons at its default level. CI
refreshes the catalog before every build.
